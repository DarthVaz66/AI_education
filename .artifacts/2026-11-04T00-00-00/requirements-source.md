# QEMU Manager — VS Code Extension

Source: Confluence page 360449, version 0.2 (ready for review). Snapshot version: 0.2.

## Мета
- Версия документа: 0.2 (ready for review)
- Изменения относительно 0.1: устранены неоднозначности REQ-04 / 06 / 09 / 10 / 11 / 12 / 20; добавлены REQ-05 (rename), REQ-06 (clone), REQ-07 (delete), REQ-18 (runtime detection), Non-Goals и NFR.
- Документ считается полным по чек-листу: границы, исключения, зависимости, критерии приёмки, нефункциональные требования, non-goals — присутствуют.

## Non-Goals
- Управление сетями, bridge-интерфейсами и DHCP не входит в scope расширения.
- Миграция VM между хостами не поддерживается.
- Автоматическое обновление QEMU / libvirt на хосте не выполняется.
- UI локализуется только на английский язык в v1; i18n-фреймворк не требуется.
- Поддержка QEMU без libvirt и без QMP не входит в scope.

## Non-Functional Requirements
- **Производительность**: активация ≤ 1.5 с на 4 ядрах / 8 ГБ RAM; операции UI ≤ 3 с до отражения результата, если иное не указано в REQ.
- **Безопасность**: секреты (токены, пароли) не пишутся в логи и настройки; телеметрия — только opt-in, без PII (см. REQ-19).
- **Доступность**: все операции доступны как VS Code commands и через Command Palette; webview-формы навигируются клавиатурой.
- **Совместимость**: VS Code 1.85+, libvirt 8.0+, QEMU 6.0+.

## Требования

### REQ-01. Активация расширения
Расширение активируется по `onStartupFinished`, при вызове любой команды расширения или при наличии файла `.qemu-manager.json` в рабочей области.
Активация не блокирует запуск VS Code: cold activation ≤ 1.5 с на референсном железе (4 ядра, 8 ГБ RAM).
При ошибке активации расширение переходит в состояние `degraded`, показывает уведомление «QEMU Manager: activation failed» с действием «Retry», и ожидает явного повторного запуска.
Acceptance criteria:
- после установки команда `QEMU: Connect` доступна в Command Palette;
- cold activation ≤ 1.5 с;
- ошибка активации не приводит к silent fail — всегда есть уведомление и действие «Retry».

### REQ-02. Управление подключениями
Пользователь может добавлять, редактировать и удалять подключения.
Подключение: имя (1–32 символа, `[a-zA-Z0-9 _-]`, уникально в рабочей области) и URI (`qemu:///system`, `qemu:///session`, `qemu+ssh://...`) либо абсолютный путь к QMP-сокету, оканчивающийся на `.sock`.
Подключения хранятся **только в workspace settings** и никогда — в user/global settings.
Поддерживается не более 10 подключений одновременно.
После перезагрузки VS Code подключения восстанавливаются; недоступное подключение отображается со статусом `disconnected` и кнопкой «Retry».
Acceptance criteria:
- добавление без обязательных полей заблокировано;
- дубликат имени → inline error «Connection name already exists»;
- после reload VS Code подключения восстановлены;
- недоступное подключение → статус `disconnected` и действие «Retry».

### REQ-03. Дерево виртуальных машин
VM отображаются в боковой панели, сгруппированные по подключениям.
Для каждой VM: имя, состояние (`running` / `stopped` / `paused` / `suspended` / `crashed`), vCPU, RAM в МБ.
Сортировка по умолчанию — по имени, case-insensitive, по возрастанию.
Состояние обновляется в соответствии с REQ-13.
Acceptance criteria:
- подключение без VM показывает placeholder «No VMs»;
- если данные VM временно недоступны — отображается последнее известное состояние с суффиксом `(stale)`;
- сортировка и группировка соблюдаются после обновления состояния.

### REQ-04. Создание VM
Форма содержит поля:
- `name`: 1–63 символа, `[a-zA-Z0-9-]`, не начинается и не заканчивается на `-`, уникально в пределах подключения. При дубликате — inline error «A VM with this name already exists in the connection»; авто-суффиксы не применяются;
- `vcpu`: целое 1–32;
- `ramMb`: 256–262144, кратно 128;
- `disks[]`: от 1 до 8 дисков; каждый — абсолютный путь на гипервизоре (родительская директория должна существовать; проверяется через libvirt), размер 1–2000 ГБ, формат `qcow2`;
- `iso` (опционально): абсолютный путь на гипервизоре, проверяется через libvirt;
- `network`: см. REQ-12.
Кнопка «Create» заблокирована, пока хотя бы одно поле невалидно (клиентская валидация по REQ-16). Валидная форма отправляется в libvirt.
Acceptance criteria:
- дубликат имени → inline error, форма не отправляется;
- невалидное числовое поле → inline error с указанием правила;
- успешное создание → VM появляется в дереве в течение 3 с;
- ошибка libvirt → уведомление (REQ-14), полный текст в логе (REQ-15), VM в дерево не добавляется.

### REQ-05. Переименование VM
Команда «Rename» доступна только для VM в состоянии `stopped`; в остальных состояниях команда disabled с tooltip «VM must be stopped».
Новое имя подчиняется правилам REQ-04 и проверяется на уникальность в пределах подключения.
Acceptance criteria:
- запущенная VM → команда disabled с tooltip;
- дубликат имени → inline error, изменения в libvirt не отправляются;
- успешное переименование → новое имя в дереве в течение 3 с.

### REQ-06. Клонирование VM
Команда «Clone» доступна только для VM в состоянии `stopped`.
Создаётся новая VM с полной копией дисков. Имя новой VM — по правилам REQ-04, уникально в подключении.
Операция показывает progress notification в VS Code и отменяема.
Acceptance criteria:
- запущенная VM → команда disabled с tooltip;
- отмена во время клонирования → частично созданная VM удаляется, исходная не изменяется;
- успешное клонирование → новая VM в дереве в состоянии `stopped`.

### REQ-07. Удаление VM
Команда «Delete» доступна только для VM в состоянии `stopped`.
Диалог подтверждения содержит: имя VM и опциональный чекбокс «Also delete disk files» (по умолчанию выключен).
Действия при подтверждении:
- undefine VM в libvirt;
- если чекбокс включён — удаление файлов дисков с гипервизора.
При любой ошибке — операция откатывается до предыдущего состояния, пользователь получает уведомление по REQ-14.
Acceptance criteria:
- подтверждение без чекбокса → VM undefined, диски остаются;
- подтверждение с чекбоксом → VM undefined, файлы дисков удалены;
- отмена → изменений нет;
- ошибка libvirt → VM остаётся в дереве, ошибка показана.

### REQ-08. Запуск VM
Команда «Start» доступна только для VM в состоянии `stopped` или `crashed`.
В остальных состояниях команда disabled.
Acceptance criteria:
- после успешного запуска состояние меняется на `running` в течение 5 с;
- при ошибке libvirt состояние не меняется, показывается уведомление с действием «Show log».

### REQ-09. Graceful shutdown
Команда «Shutdown» отправляет ACPI-запрос завершения.
Таймаут берётся из workspace settings: целое 5–300 секунд, по умолчанию 30.
По истечении таймаута показывается диалог с действиями: «Force stop» / «Wait more» / «Cancel».
- Force stop → выполняется REQ-10;
- Wait more → таймер перезапускается с тем же значением;
- Cancel → диалог закрывается, состояние VM не меняется.
Acceptance criteria:
- таймер использует значение из настроек в секундах;
- диалог появляется по истечении таймаута;
- «Force stop» вызывает REQ-10;
- «Cancel» не меняет состояние VM.

### REQ-10. Force stop
Команда «Force stop» немедленно завершает процесс VM.
Перед выполнением показывается подтверждение с именем VM и предупреждением «Unsaved data may be lost».
Подтверждение можно отключить настройкой `qemuManager.confirmForceStop` (по умолчанию `true`).
Acceptance criteria:
- подтверждение содержит имя VM;
- отмена подтверждения не меняет состояние;
- после force stop состояние становится `stopped` в течение 3 с.

### REQ-11. Пауза и возобновление
«Pause» доступна для `running`, «Resume» — для `paused`. В остальных состояниях команды disabled.
Acceptance criteria:
- успешный pause → состояние `paused` в течение 3 с;
- успешный resume → состояние `running` в течение 3 с;
- ошибка libvirt → состояние не меняется, ошибка показана.

### REQ-12. Сетевая конфигурация
Поле `networkType`: `user-nat` (по умолчанию) или `bridged`.
- Для `bridged`: пользователь выбирает bridge из списка, полученного от libvirt. Если список пуст → опция `bridged` disabled с tooltip «No bridges available on host».
- Для `user-nat`: если IP определим — отображается в дереве; если нет — отображается `unknown` без влияния на рендеринг дерева.
Acceptance criteria:
- `bridged` без доступных интерфейсов → опция disabled с tooltip;
- `user-nat` с неопределимым IP → в дереве `unknown`;
- `bridged` с выбранным интерфейсом → VM создаётся с указанным bridge.

### REQ-13. Автообновление состояния
Интервал обновления — workspace setting: целое 1–60 секунд, по умолчанию 5; значение `0` означает «только ручное обновление».
При поддержке libvirt events (проверка возможностей через `virConnectIsAlive` + capability probe) расширение подписывается на события вместо polling.
Если подписка на события невозможна — расширение откатывается к polling, пишет warning в лог (REQ-15) и не показывает пользователю ошибку.
Кнопка «Refresh» в дереве доступна всегда.
Acceptance criteria:
- интервал `0` → только ручное обновление;
- события поддерживаются → polling не выполняется (проверяется по логу);
- ошибка подписки на события → polling продолжается, warning в логе.

### REQ-14. Обработка ошибок
Все ошибки libvirt/QMP маппятся в пользовательские сообщения по таблице соответствий, покрывающей минимум: connection refused, auth failed, VM not found, operation not supported, disk full, resource busy.
Пользователь видит уведомление: friendly message + действия «Show log» и «Dismiss» («Show log» — только для ошибок с диагностической ценностью).
Полный сырой текст ошибки (stack, request, response) пишется в Output Channel с timestamp.
Не замапленная ошибка → «Unexpected error: {code}» с действием «Show log».
Acceptance criteria:
- любая libvirt-ошибка → уведомление без raw stack trace в тексте;
- «Show log» открывает Output Channel и фокусирует последнюю запись;
- unmapped errors попадают в fallback-ветку.

### REQ-15. Логирование
Output Channel «QEMU Manager». Формат строки: `YYYY-MM-DDTHH:MM:SSZ [LEVEL] [conn:vm] message`.
Ring buffer: последние 10 000 строк, более старые отбрасываются.
Уровень логирования — workspace setting: `error` / `info` / `debug` (по умолчанию `info`).
Acceptance criteria:
- каждая команда → запись уровня `info` или `debug`;
- ошибочные ответы → запись уровня `error`;
- размер буфера ограничен 10 000 строками;
- изменение уровня применяется немедленно.

### REQ-16. Валидация входных данных
Все поля формы создания VM валидируются на клиенте по правилам REQ-04 до отправки в libvirt.
Ошибки показываются inline рядом с полем с текстом, отражающим нарушенное правило (например, «RAM must be between 256 and 262144 MB, multiple of 128»).
Невалидные значения не отправляются в libvirt.
Серверные ошибки валидации libvirt показываются по REQ-14.
Acceptance criteria:
- пустое / нечисловое / выходящее за границы / некратное значение → inline error, submit disabled;
- текст / длина / недопустимые символы / дубликат имени → inline error, submit disabled;
- валидная форма → submit enabled и валидация проходит.

### REQ-17. Горячие клавиши
По умолчанию: `Ctrl+Shift+Q` (macOS: `Cmd+Shift+Q`) → Start; `Ctrl+Shift+W` (macOS: `Cmd+Shift+W`) → Shutdown.
Комбинации настраиваются через стандартный Keybindings UI VS Code.
При конфликте с другими расширениями действует штатное предупреждение VS Code; расширение не переопределяет чужие биндинги.
Команда срабатывает только если выбрана VM и команда применима к её состоянию.
Acceptance criteria:
- дефолтный биндинг выполняет команду для выбранной VM в применимом состоянии;
- при неприменимом состоянии VM биндинг не срабатывает;
- пользовательский биндинг через Keybindings JSON работает.

### REQ-18. Кроссплатформенность и runtime detection
Поддерживаемые ОС: Windows 10+, macOS 12+, Ubuntu 22.04+.
Требования к runtime: libvirt 8.0+ либо QEMU 6.0+ с QMP-сокетом.
При отсутствии runtime — при активации показывается уведомление «QEMU Manager: libvirt/QEMU not detected» с действием «Show setup instructions»; расширение переходит в состояние `degraded`, дерево пустое, команды возвращают friendly-ошибку по REQ-14.
Acceptance criteria:
- расширение устанавливается и активируется на всех трёх ОС;
- отсутствие runtime → показ инструкции по установке;
- состояние `degraded` не приводит к падению или зависанию VS Code.

### REQ-19. Телеметрия (opt-in)
Телеметрия по умолчанию отключена. Включается только явно: через first-run prompt или настройку `qemuManager.telemetry.enabled`.
Payload содержит только: тип действия (например, `vm.start`), success/failure, код ошибки (если есть), `duration_ms`, версию расширения, семейство ОС (`windows` / `macos` / `linux`).
Payload **не содержит**: имена VM, пути к файлам, IP-адреса, URI/пользователей подключений, hostname.
Acceptance criteria:
- телеметрия выключена → никаких сетевых вызовов от телеметрии;
- телеметрия включена → payload соответствует схеме выше;
- отказ от first-run prompt → настройка остаётся `false`, повторный prompt не раньше чем через 30 дней.

### REQ-20. Экспорт и импорт конфигурации VM
Экспорт создаёт JSON со схемой `qemuManager.vmConfig` версии 1.
Поля: `name`, `vcpu`, `ramMb`, `disks[]` (`path`, `sizeGb`, `format`), `network` (`type`, `bridge` для bridged), `iso`.
Импорт:
- валидирует версию схемы — принимается только `1`; иначе ошибка «Unsupported config version: {version}» и импорт прерывается;
- валидирует обязательные поля по правилам REQ-04;
- если VM с таким именем уже существует в целевом подключении — показывается подтверждение «VM '{name}' already exists. Overwrite?» (по умолчанию `Cancel`);
- при любой ошибке валидации — отчёт с построчными сообщениями, импорт прерывается без частичных изменений.
Acceptance criteria:
- экспорт → валидный JSON, все обязательные поля присутствуют;
- импорт валидного конфига без конфликта → VM создана;
- импорт валидного конфига с конфликтом → подтверждение overwrite;
- импорт невалидного конфига → отчёт, VM не создана.
