# Skill: requirement-review

## Purpose

Дать методику анализа требований на противоречия, неоднозначности и полноту.
Не описывает, как вызывать MCP и куда сохранять артефакт — это контракт агента
`requirement-reviewer`.

Скилл отвечает на вопросы:
- как искать противоречия, неоднозначности и пробелы полноты;
- как присвоить severity, не завышая её;
- как нормализовать версию требований для трассировки;
- какие наблюдения не являются finding'ами и не должны попадать в артефакт.

## 1. Ambiguity detection

Помечай требование как ambiguous, если встречается:
- **Кванторы без границ**: "many", "some", "fast", "usually", "as needed",
  "если возможно".
- **Дизъюнкции без критерия выбора**: "A или B" без правила выбора.
- **Неопределённые термины**: слово, не введённое в глоссарии документа.
- **Пассив без субъекта**: "будет обработано", "должно поддерживаться".
- **Числа без диапазона**: "несколько", "достаточно", "оптимально".

Для каждой находки укажи: цитату, минимум 2 альтернативные интерпретации,
что нужно уточнить.

## 2. Contradiction detection

Проверяй три вида конфликтов:
- **Прямое противоречие**: два требования утверждают несовместимое
  (A обязателен / A запрещён).
- **Конфликт ограничений**: числовые диапазоны, лимиты, таймауты не пересекаются.
- **Нарушение жизненного цикла**: состояние или переход в REQ-X запрещён
  предусловием в REQ-Y.
- **Scope-конфликт**: требование предписывает функцию, которая в Non-Goals
  объявлена вне scope (или наоборот).

Метод: pairwise comparison + построение state machine по требованиям,
описывающим состояния. Для каждой находки — обе ссылки на требования
и минимальный воспроизводящий сценарий.

## 3. Completeness checklist

Для каждого требования проверь наличие:
- **Границы**: входные диапазоны, лимиты, размерности.
- **Исключения**: что при ошибке / отмене / таймауте / недоступности зависимости.
- **Зависимости**: внешние системы, версии, платформы.
- **Проверяемые AC**: измеримый критерий приёмки.
- **Нефункциональные аспекты**: производительность, безопасность, доступность —
  если применимо.

Плюс на уровне документа:
- **Non-Goals** зафиксированы и не противоречат требованиям.
- **NFR** вынесены явно.
- **Глоссарий** отсутствует или согласован.
- **Все состояния из UI-списков** имеют хотя бы одну REQ, которая в них
  переводит или из них выводит. Состояние без переходов — completeness-находка.

## 4. Severity rubric

- **blocker** — затрагивает безопасность, данные, деньги, юридические
  обязательства, **или** блокирует проектирование: ни одна интерпретация
  требования не позволяет построить тестируемый AC.
- **critical** — меняет объём или поведение системы; нельзя двигаться в design
  без решения, **но** тестируемый AC существует при одной из интерпретаций.
- **major** — деградирует качество, но проектирование возможно с явным
  задокументированным допущением.
- **minor** — редакционное, не влияет на поведение.

### Тест на blocker

Finding может быть blocker только если **одновременно** верно:

1. затрагивает безопасность / данные / деньги / юридические обязательства;
2. **или** ни одна интерпретация требования не позволяет построить
   детерминированно проходящий или падающий AC.

Проверка: «Можно ли из текущего текста требования вывести хотя бы один
Given/When/Then, который пройдёт или упадёт детерминированно при любой
из допустимых интерпретаций?»

- Если да — это **не** blocker. Даже если AC требует явного допущения,
  это **major**.
- Если нет ни при какой интерпретации — blocker.

### Тест на critical

Finding может быть critical, если:

1. design невозможен без решения, **но**
2. AC существует при одной из интерпретаций (одна ветка тестируема,
   другая — нет).

Пример critical: «rollback противоречит необратимости удаления» — AC для
успешного удаления есть, AC для rollback нереализуем. Design возможен
только с решением, какая ветка главная → critical.

Пример не-critical: «Non-Goals противоречит REQ» — при интерпретации
«выбор существующего bridge ≠ управление bridge» все AC тестируемы →
major, не blocker.

## 5. Формат находки

Каждая находка содержит:
- `id` — уникальный в отчёте (`F-001`, `F-002`, ...);
- `category` — `contradiction` / `ambiguity` / `completeness`;
- `severity` — по rubric раздела 4;
- `requirement_refs[]` — ID требований и/или секций документа (`Non-Goals`, `NFR`);
- `evidence` — цитата или ссылка, подтверждающая находку;
- `impact` — что именно сломается в design / tests, если не устранить;
- `recommendation` — что уточнить или дописать.

## 6. Нормализация requirement_version

Версия требований извлекается из поля «Версия документа» по паттерну
`\d+\.\d+(\.\d+)?`. Аннотации в скобках (`ready for review`, `draft`,
`approved`, `final`) в `requirement_version` **не включаются** — они
попадают в отдельное поле `requirement_status`:

```json
{
  "requirement_version": "0.2",
  "requirement_status": "ready_for_review"
}
```

Маппинг аннотаций:

| Аннотация в документе | `requirement_status` |
|---|---|
| `draft`, `черновик` | `draft` |
| `ready for review`, `на ревью` | `ready_for_review` |
| `approved`, `утверждено` | `approved` |
| `final`, `финал` | `final` |
| отсутствует | `unspecified` |

Нормализованная версия используется для:
- `meta.json.requirement_version`;
- resume по совпадению версии;
- cross-check Gate 2c между `01`, `02`, `03`.

Если версия не извлекается паттерном (например, `v0.2-beta`) — использовать
строку как есть, но зафиксировать в `blocking_reason` пометку
`requirement_version_format_nonstandard`.

## 7. Антипаттерны ревью (что не считать finding'ом)

- **Реализационное решение** — если в требовании не указан механизм
  (например, «bridge-list от libvirt» без указания метода), это не
  finding, а естественная свобода реализации. Finding появляется только
  если разные механизмы дают разные AC.
- **Стилистика** — формулировки, орфография, оформление не являются
  finding'ами, если не меняют поведение.
- **Отсутствие деталей вне scope** — если тема явно в Non-Goals, её
  отсутствие в требованиях не является пробелом.
- **Предположение о будущих требованиях** — «здесь может понадобиться X,
  которого нет» — не finding, если X не вытекает из существующих REQ.
- **Дубль существующего finding'а** — если F-003 и F-007 описывают один
  и тот же корень, объединяй в один finding с несколькими
  `requirement_refs`, а не размножай severity.
- **Завышение severity** — blocker без прохождения теста раздела 4 не
  является blocker'ом. Пересмотри severity, если AC существует хотя бы
  при одной интерпретации.
