# Skill: test-design

## Purpose

Дать методику построения тестовой модели для публикации в Testomat.io.
Не описывает контракт артефакта, права на инструменты и куда сохранять —
это зона инструкции агента `test-designer`.

Скилл отвечает на вопросы:
- как извлечь тестовые условия из требования;
- какие техники применить для positive / negative / boundary;
- как определить применимость типа и обосновать N/A;
- как присвоить priority, совместимый с Testomat.io;
- как оформить шаги и expected, чтобы кейс был диагностируемым;
- как проверить результат перед сохранением.

## 1. Извлечение тестовых условий

Из требования вытаскивай:
- **Существительные** → сущности и состояния (VM, snapshot, connection).
- **Глаголы** → действия и переходы (start, stop, rename).
- **Ограничения** → границы и диапазоны (1–32 vCPU, 256–262144 MB).
- **Ветвления** → условия и их комбинации («если bridge недоступен → опция disabled»).

Одно тестовое условие = один проверяемый факт. Не смешивай условия
(«start VM и проверка лога» — это два условия).

## 2. Positive design

Минимум:
- один happy path на каждый AC;
- альтернативные успешные пути (валидные вариации входа).

Positive-кейс всегда заканчивается ожидаемым успешным результатом.

## 3. Negative design

Обязательно покрывай классы:
- **Invalid input**: неверный тип, пустое, слишком длинное, недопустимые символы.
- **Boundary violation**: за пределами диапазона (см. п.4).
- **Precondition violation**: действие в недопустимом состоянии (start для running).
- **Permission/role denial**: если есть роли.
- **Dependency failure**: недоступность libvirt, bridge, диска.

Negative-кейс ожидает **конкретную** ошибку, а не «что-то пошло не так».
Если требование не описывает сообщение об ошибке — ожидаемый результат
формулируется как наблюдаемое состояние (например, «submit disabled, inline
error показан рядом с полем ramMb»), а не как текст сообщения.

## 4. Boundary design

Порядок:
1. **Equivalence partitioning** — разбей диапазон на классы (валидный, ниже, выше).
2. Для каждого класса — **boundary values**: min-1, min, min+1, max-1, max, max+1.
3. Для строк — **length boundaries** (0, 1, max-1, max, max+1) и
   **format boundaries** (недопустимые символы, ведущий/замыкающий спецсимвол).
4. Для множеств — **empty, single, full, over-limit**.
5. Для перечислимых вариантов (enum) — границы не применимы; вместо них
   проверяются все значения enum (positive) и невалидное значение (negative).

Boundary-кейс = один тест на одно граничное значение; не объединяй min и max
в один кейс.

## 5. Специальные техники (когда применимо)

- **State transition** — если требование описывает lifecycle: покрывай все
  разрешённые переходы и все запрещённые переходы (negative).
- **Decision table** — если есть ≥ 3 условий с комбинациями: покрывай все
  значимые комбинации, не полный декартов продукт.
- **Pairwise** — если комбинаций слишком много: попарное покрытие.
- **Error guessing** — после формальных техник: типичные сбои (race, timeout,
  disk full, потеря соединения в середине операции).

## 6. Формат шагов и expected

Каждый кейс — это последовательность пар `step` + `expected`. Это требование
контракта Testomat.io (Markdown Classical Tests): шаг без expected считается
неполным.

Правила:
- **один `step` = одно атомарное действие** пользователя или системы.
  «Открыть форму и ввести имя» — это два шага.
- **`expected` привязан к шагу**, а не ко всему кейсу. Это наблюдаемый
  результат именно этого шага.
- **Финальный `expected` последнего шага** = итоговый проверяемый результат
  кейса.
- Если промежуточный шаг не даёт наблюдаемого результата (подготовка) —
  `expected = "—"`. Не пропускай шаг.
- **Не объединяй** в один шаг проверки разных атрибутов («состояние running
  и RAM 4096» — это два шага с двумя expected).
- **Precondition** — это исходное состояние до первого шага, а не первый шаг.
  Если для запуска кейса нужно действие (создать VM, запустить libvirt) —
  вынеси это в `precondition`, а не в `steps`.

Anti-pattern: один шаг + 5 проверок в одном expected. Такой кейс
недиагностируем при падении: непонятно, какая проверка провалилась.

## 7. Присвоение priority

Priority присваивается по **бизнес-импакту сбоя**, не по типу кейса.
Допустимые значения Testomat.io: `low` / `normal` / `important` / `high` / `critical`.

Rubric:

- **critical** — сбой приводит к потере данных, нарушению безопасности,
  недееспособности VM или невозможности восстановиться без ручного вмешательства.
  Пример: Force stop с неподтверждённой потерей данных; удаление VM с дисками
  без возможности отката; импорт конфигурации с перезаписью существующей VM
  без подтверждения.
- **high** — сбой блокирует основной пользовательский сценарий без обходного пути.
  Пример: невозможно запустить VM из stopped; невозможно создать VM при
  валидном вводе; невозможно подключиться к гипервизору.
- **important** — сбой ломает побочный сценарий или деградирует UX, но
  обходной путь есть. Пример: Rename не обновляет дерево до ручного Refresh;
  stale-маркер не показывается; ошибка libvirt отображается без кнопки
  «Show log».
- **normal** — сбой затрагивает edge-case, редкий сценарий или косметику.
  Пример: неверный порядок сортировки; tooltip не показан; placeholder
  «No VMs» отсутствует.
- **low** — сбой не влияет на поведение пользователя. Пример: warning записан
  не в тот уровень логирования; формат timestamp слегка отличается; текст
  уведомления отличается формулировкой, но смысл сохранён.

Правила присвоения:
- negative-кейс на потерю данных / безопасности → минимум **high**, обычно **critical**;
- negative-кейс на отказ основного сценария → **high**;
- boundary-кейс наследует priority от своего positive-кейса;
- N/A-кейсы (не применимые типы) priority не имеют и в артефакт не попадают;
- один кейс — один priority, не диапазон.

## 8. Применимость типов и N/A

- **positive** применим всегда.
- **negative** неприменим, если требование не описывает ни ошибок, ни
  недопустимых входов (например, чисто информационное требование).
- **boundary** неприменим, если у требования нет числовых, диапазонных или
  лимитных условий.

Для каждого N/A — обязательная запись в `coverage_summary`:
`type` и `reason`. Reason должен быть конкретным: не «не применимо»,
а «нет числовых или лимитных условий» / «требование описывает дискретные
переходы, а не диапазон» / «перечислимые варианты, не диапазон».

## 9. Проверка покрытия (self-check перед сохранением)

- [ ] каждое AC требования покрыто ≥ 1 positive-кейсом;
- [ ] каждая ветка ошибки покрыта ≥ 1 negative-кейсом (или N/A с reason);
- [ ] каждое числовое / диапазонное / лимитное ограничение покрыто полным
      boundary-набором (min-1, min, min+1, max-1, max, max+1) или N/A с reason;
- [ ] каждый transition и запрещённый transition покрыт (для lifecycle-требований);
- [ ] у каждого кейса заполнены `step` + `expected` для всех шагов;
- [ ] у каждого кейса присвоен `priority` по rubric п.7;
- [ ] нет кейсов без `requirement_ref`;
- [ ] нет кейсов с ожиданием «не падает» без конкретного наблюдаемого результата;
- [ ] все N/A в `coverage_summary` имеют конкретный `reason`;
- [ ] title кейса без переносов строк (совместимость с Testomat.io create).

## 10. Anti-patterns (не делать)

- Кейс «проверить, что всё работает» — не проверяемый.
- Дубль positive с инвертированным ожиданием — это не negative, а регресс.
- Кейс без `requirement_ref` — «придуманный», должен быть удалён.
- Один шаг с несколькими expected — недиагностируемо при падении.
- Priority «critical» для косметических дефектов — размывает rubric.
- N/A без reason — скрывает непроработанное требование.

## 11. Совместимость с bulk-публикацией (опционально)

Если оркестратор использует `testomat_tests` с `command: "bulk_upsert"`
(Markdown Classical Tests), каждый кейс должен без потерь конвертироваться:

- `title` — строка без переносов;
- `precondition` → секция «Preconditions»;
- `steps` → нумерованный список пар «step → expected»;
- `type` (positive / negative / boundary) → tag, не часть title;
- `requirement_ref` → tag `req:{id}`;
- `priority` → поле priority в Markdown-заголовке.

Обычный режим через N × `create` работает без этого требования —
конвертация выполняется на этапе Publish.
